## Residual Questions

1. **Ed decision required:** should device enrollment narrow asymmetric self-service to `external_consumer`/`installation`, or should personal `user_principal` enrollment remain valid? This spike preserves the latter. Narrowing gives a crisp device class but withdraws a shipped declaration option; preserving it leaves “device” a convention until the future registration protocol can name a device binding honestly.
2. The app-purpose registry uses one associative config mapping (`app.id => package_purpose`). If P5-UI needs display metadata or several UI operations under one app id, keep that metadata outside this authorization mapping rather than turning the value into a list that weakens exactly-one mapping.
3. Root retirement has no ordinary revoke/offboard path in this spike. Emergency rotation immediately ends the superseded root, but intentionally ending the sole current root would need a separately named dedicated lifecycle operation if the production contract requires “no current signer” as an operator state.

## Where The Coordinator Map Was Wrong Or Incomplete

- S3's `onboard` bearer is necessarily an exception to S1's generic bearer/external-consumer purpose matrix. The smallest consistent rule is “generic mint refuses enrollment; the bounded claim-scope producer derives it.”
- The snapshot is P5a, so S2's MCP and onboarding statements describe post-P5c/P5d code, not the code this spike started from. The spike had to cross those future rebase seams to make purpose executable.
- “Root retirement stays inside its own lifecycle” also requires ordinary `RevokeCredential` refusal, not only the offboarding policy named in S5.
- Exactly-one app mapping is executable as an associative scalar map, but D-UI-3's prose calls the UI value a list. P5-UI must keep its offered-id list separate from this id-to-protocol authorization registry.
